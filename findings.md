## Research Findings

- The project is a JavaScript monolith split across a React/Vite frontend and an Express backend, but both sides centralize major business logic into a handful of oversized files.
- The backend persists most business state in SQLite as JSON blobs inside `kv_store`, including declaration rows, MST assignments, KPI rules, teams, accounts, alerts, and schedules.
- Several routes appear to trust unauthenticated requests or request-supplied `actor` values for sensitive operations; this is more than a code-quality issue and may be a security issue.
- The repo copy baseline is now runnable again: dependency integrity is restored, `pnpm healthcheck` passes, `pnpm lint` is warnings-only, and `tests/server.api.test.js` passes in full.
- The repo already contains partial planning documents for UX and Windows/SQL 2008 compatibility, but there is no unified v4 modernization blueprint.
- `/api/bootstrap` is currently called before the app establishes user auth state and appears to return a near-full storage snapshot.
- `/api/auth/accounts*` routes appear to allow account lifecycle operations without route-level authorization.
- Hardcoded default passwords still exist in backend seed logic, and plaintext passwords exist in `server/data/db.json`.
- The clean replacement for shipped default credentials is an env-backed bootstrap contract per account, with an explicit admin alias (`KPI_BOOTSTRAP_ADMIN_PASSWORD`) plus normalized username keys (`KPI_BOOTSTRAP_PASSWORD_<USERNAME>`).
- The runtime should only require the admin bootstrap secret when the database is empty or the admin account is missing. Existing populated environments should keep booting from persisted account rows without forcing bootstrap env variables at startup.
- `ui-ux-pro-max` returned a strong fit for a data-dense drill-down dashboard pattern; that aligns with the product but typography should be adjusted for Vietnamese readability.
- Once `/api/bootstrap` is protected, the frontend needs an authenticated re-bootstrap path after login or session restore; otherwise a secure backend would starve the client cache.
- The import surface had more open read/config endpoints than the first review excerpt listed, including declaration search and CO-related config/state reads.
- The next highest-value cleanup target is still auth-model consistency: the frontend keeps contradictory local token state while the backend trusts cookie sessions.
- Phase 1A slice is now underway with verified client-side auth cleanup: the frontend no longer stores `kpi_session_token` or injects bearer headers, and instead always relies on cookie-backed `credentials: 'include'` requests.
- Demo mode and frontend auth mocks were aligned with the cookie-session model so tests no longer depend on token echoes from mock auth APIs.
- Backend auth responses were tightened too: login and password-change now return `expiresAt` and cookie headers, but no longer echo session `token` values into JSON payloads.
- Leftover client-side actor plumbing was removed from `AccountManager`, so the UI no longer sends dead `actor` metadata for account lifecycle actions.
- The clean RBAC enforcement model for the current codebase is now explicit:
  - session boundary: `requireAuthenticated()`
  - account lifecycle: `requireAccountManage()`
  - storage access: `verifyStoragePermission()`
  - specialized operational routes: dedicated guards such as `requireAdminSyncManage()`, `requireAlertsManage()`, `requireAuditView()`, `requireAiAssistUsage()`, `requireAiAssistManage()`, `requireRulesManage()`, and `requireNotificationAccess()`
- With Phase 1A closed, the next architectural risk is the data model itself: `kv_store` blob keys need a concrete PostgreSQL migration map.
- The PostgreSQL target should not treat every former blob key equally: core business entities move to typed tables, while low-value operational configs stay in JSONB-backed config storage.
- KPI aggregation must be versioned by rule set. Current behavior recomputes KPI from raw declarations under the active rules, so precomputed monthly aggregates without a `rule_set` dimension would be wrong.
- The cleanest replacement for `mst_rows_v2` is a temporal table with a Postgres `daterange` and an exclusion constraint on overlapping periods per MST.
- The current AI/reporting path should eventually read from Postgres aggregates instead of rebuilding snapshots from raw declaration blobs plus approved adjustments on every request.
- A safe first TypeScript cut exists now under `server-v4/`: it is intentionally isolated from the legacy runtime and exposes only `/api/v4/health`, `/api/v4/meta/modules`, and per-module `__meta` endpoints.
- The v4 scaffold has an explicit eight-domain registry: auth, declarations, mst-assignments, teams, hq-agencies, kpi-rules, kpi-adjustments, and reporting.
- `server-v4` now has its first non-meta runtime domains: `teams` and `mst-assignments` are served through typed repository/service/controller stacks that read the legacy SQLite `kv_store` directly, without importing the monolith backend.
- `server-v4` now also serves read-only `declarations` and `kpi-rules` through the same typed boundary. The declaration adapter preserves current declaration-number normalization while exposing stable IDs and query filters, and the rules adapter wraps legacy single-rule snapshots into a versioned collection response.
- `server-v4` now also serves reporting routes through `/api/v4/reporting/summary`, `/staff`, `/teams`, and `/schedules`, plus schedule `POST`/`DELETE` mutations; this proves the reporting boundary can move without reusing the `server/index.js` monolith directly.
- The safest short-term bridge for reporting is to reuse `src/lib/reports.js` `buildReportData()` behind an async loader, instead of forking KPI math before PostgreSQL aggregates exist.
- The monolith now also exposes `/api/v4/reporting/summary`, `/staff`, `/teams`, and `/schedules` as authenticated shim routes backed by the same legacy KPI math. That gives the frontend a stable cutover contract without forcing a separate `server-v4` deployment first.
- The export boundary is tighter now: `/api/reports/export` can rebuild report payloads from a compact `reporting-v4` contract (`source`, `query`, `ruleId`, `staffKey`/`teamKey`, `columns`) and no longer needs to trust large client-posted report blobs for the new path.
- `ReportViewer` still computes `buildReportData()` in the browser for the interactive screen, so the export hardening is an incremental server-side safety win rather than the final reporting cutover.
- Reporting schedule writes now sit behind the reporting boundary too: the monolith shim exposes `POST /api/v4/reporting/schedules` and `DELETE /api/v4/reporting/schedules/:id`, and generic storage `PUT`/`DELETE` writes for `kpi_report_schedule_v1` are blocked.
- Reporting projection persistence is now materially less blob-shaped: active/default monthly aggregates and schedules materialize typed projection rows in both SQLite and Postgres adapters, so the next `F5` gap is read-model convergence, not schedule ownership.
- `server-v4` `/api/v4/reporting/view` now also resolves through `server/reportingReadModels.js`, so compact export, runtime routes, and dashboard/client tests all lock the same reporting read-model contract; the remaining reporting residue is UI/module split and jsdom chart noise, not backend contract drift.
- `ReportViewer` no longer depends on store-backed schedule overlays or schedule-key subscriptions. Schedule save/delete now go through `reportingClient`, and the shared reporting schedule cache updates the UI directly after each mutation.
- The earlier `server-v4` vite-node loader problem is now retired: reporting math has been extracted into shared modules, so `server-v4` no longer needs to import `src/lib/reports.js` via runtime file-URL tricks.
- Both the monolith shim and `server-v4` can now serve a combined reporting view bundle from `/api/v4/reporting/view`, which lets the dashboard read path cross the reporting boundary in a single request instead of rebuilding the view model from three browser-side fetches.
- The root flat ESLint config had no TypeScript parser/plugin path for `server-v4`, so the extracted post-cutover runtime could pass `tsc` while still sitting outside real lint coverage.
- The lowest-risk hardening slice is a targeted `server-v4` lint boundary around app/bootstrap/http/legacy/persistence/reporting files, not a one-shot lint enablement for the entire TypeScript tree.
- Windows `linebreak-style` enforcement on root JavaScript files conflicts with local `LF` working copies under the repo's `autocrlf` behavior; a file-specific override for `eslint.config.js` is cleaner than mass-normalizing the repo or loosening the general JS rule.
- Monolith startup already backfills declarations, MST assignments, teams, KPI rules, and adjustments into typed snapshot tables, so `server-v4` fallback reads from `kv_store` blobs for those business hot paths are compatibility-only rather than required bootstrap behavior.
- Retiring those business blob fallbacks safely requires test fixtures to materialize typed snapshots from seed data directly; otherwise `server-v4` regressions keep passing for the wrong reason by leaning on the same legacy blobs the runtime is supposed to stop reading.

## Technical Decisions

| Decision                                                                                                                            | Rationale                                                                                                                                                    |
| ----------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Focus findings on security, architecture, data model, and operability first                                                         | These dominate both business risk and refactor cost                                                                                                          |
| Use UI skills for design-system and workflow recommendations, not only visual commentary                                            | The user explicitly requested UI/UX optimization, and the UI problems are structural                                                                         |
| Recommend staged migration over a one-shot rewrite                                                                                  | The system has many operational features and business rules that would be easy to lose in a rewrite                                                          |
| Put the long-form review in `docs/system-v4-review-plan.md`                                                                         | Keeps the review persistent and reusable in later implementation turns                                                                                       |
| Track the execution program under epic `cng-7c8`                                                                                    | Review is done; implementation now needs phase-by-phase control                                                                                              |
| Start implementation with security hardening (`cng-7c8.1`)                                                                          | Broken trust boundaries are the highest-risk defects in the current codebase                                                                                 |
| Treat the remaining ESLint output as legacy warning debt, not a blocker to migration work                                           | The baseline now has `0` lint errors and `61` warnings, so the repo is usable again                                                                          |
| Move next to `cng-7c8.3` instead of spending more time polishing Phase 0                                                            | The highest remaining design risk is auth/session inconsistency, not tooling breakage                                                                        |
| Remove bearer-token behavior from the frontend before changing backend auth responses                                               | This shrinks the XSS/session surface first while keeping the backend contract change isolated for the next slice                                             |

## Current Residual Risks

- The new monthly aggregate path is still materialized on request and cached back into legacy `kv_store`; it improves contract shape and reuse, but it is not yet a true background precompute pipeline with invalidation/versioning.
- The new write-time refresh now coexists with a canonical default monthly preset for schedules and no-query reads, but exports and other dashboard/report consumers still do not share a broader preset aggregate strategy yet.
- Reporting routes still depend on legacy declaration normalization behavior; the new lazy-read/cache-order fix prevents accidental cache eviction, but the deeper source-read path should still be pulled behind explicit projection jobs in a later slice.
- The export route no longer trusts raw client report blobs for the compact `reporting-v4` path, but the dashboard still derives report state in-browser and only uses the compact contract when exporting; full convergence on shared read models is still pending.
- Reporting chart rendering is now isolated behind an explicit jsdom harness in `vitest.setup.js`; future reporting/chart tests should keep using that accepted seam (and direct warning assertions where needed) instead of relying on stderr noise or reintroducing implicit zero-size container behavior.
- The new `companies` read-model contract removes browser-side recomputation, but company identity completeness still depends on what legacy declaration rows actually carry; sparse legacy fixtures can legitimately produce blank `mst`/`cong_ty` while still yielding correct KPI totals and staff/team grouping.
- `reportingClient` previously still paid a browser-side dedupe cost to build `report.rows` even though `ReportViewer` no longer consumed it; that path is now removed, so any future need for a cross-staff raw-row snapshot should be justified explicitly rather than recreated implicitly.
- `reportingClient` also previously mirrored collection-level `keysHash` strings from the server into the browser view model without a consumer; that metadata is now stripped client-side, so future reintroduction should only happen if the UI genuinely needs hash-aware invalidation or display behavior.
- `reportingClient` also mirrored `trend.teamSeries` and `trend.topTeams` into the browser model even though `ReportViewer` only reads `trend.series` and `trend.comparison`; those fields are now left out client-side to keep the normalized model closer to actual UI needs.
- `reportingClient` staff/team normalizers also used to spread entire server item payloads into browser state; that meant any newly-added server field would silently become client state even with no consumer. The normalizers now emit an explicit item shape, which reduces accidental browser-state growth and makes future payload changes easier to reason about.
- `reportingClient` top-level `summary` previously passed through the raw server summary object as-is; that meant server-only summary metadata could silently become browser state. The client now normalizes `summary` to the concrete KPI metrics the current dashboard renders.
- `reportingClient` rule fallback also used to spread the full matching `currentRules` object into browser state. That leaked nested rule metadata like exclude-agency details and arbitrary server-only fields even though the reporting UI only needs identity/display fields plus excluded license codes. The client now normalizes `report.rules` to that explicit subset.
- `ReportViewer` previously still contained a mini-normalizer for `adjustments.totalsByCategory`, including a legacy `totals` alias fallback. That shaping now lives in `reportingClient`, which keeps the render path thinner and makes the adjustment contract consistent across empty/live states.
- Approved adjustment rows also used to be consumed as raw detail rows with nested `adjustment` blobs, forcing `ReportViewer` to pull out `label`, `quantity`, `unitPoints`, references, and notes inline while rendering. The client model now flattens that branch into a render-ready shape, which reduces UI coupling to the legacy detail-row structure.
- Even after those payload cleanups, `ReportViewer` still carried a redundant `adjustmentsReport` rebuild and two dead locals in the same path. Those are now removed; the component reads the canonical `report.adjustments` contract directly and the targeted reporting lint path is clean again.
- Staff/team detail cards were still deriving `licenseSummary` from `stats.licenseCodes` and `adjustmentTotals` from `adjustmentSummary` locally in two separate places. Those fields now come pre-normalized from `reportingClient`, which removes duplicate shaping from the browser path without changing the underlying detail metrics contract.
- Staff/team detail cards also still rescanned raw `rows` to count positive/negative/neutral adjustment entries and total applied points. That aggregate is now normalized once as `adjustmentMetrics` in `reportingClient`, so the cards only format already-computed metrics instead of recomputing them twice in the UI.
- The top-level adjustments summary still had one leftover browser-side transform: `ReportViewer` converted `adjustments.totalsByCategory` into an ordered array itself. `reportingClient` now emits `adjustments.totalsList`, which removes the last direct `toAdjustmentTotalsArray()` call from the reporting browser path.
- Team-member rows plus the staff/team summary tables were still joining `stats.licenseCodes` inline during render. Those paths now consume normalized `licenseSummary` strings from the reporting client model, which removes another repeated browser-side string-shaping step.

- `ReportViewer` now reads canonical schedule summaries plus `aggregateStatus` from `/api/v4/reporting/schedules`, and schedule save/delete also use reporting-boundary helpers instead of store-backed overlays. Both the monolith shim and `server-v4` now expose that schedule mutation contract.

## 2026-03-14 Smoke Gate Pool Disposal Regression (`cng-q7u`)
